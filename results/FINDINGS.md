## Summary

A skill can branch on vendor and harness for both pairs tested here: "the Claude pair" means Opus, Sonnet and Haiku in Claude Code, and "the Codex pair" means Codex with OpenAI's Luna model. Branches on exact model version, on tier and on capability answered from product knowledge worked for the Claude pair only. The Codex pair reported a family name instead of its model, placed itself at the top of its lineup whether or not that cost it work, and guessed its harness's features differently from run to run. A capability branch that checks the session's tools worked for the Claude pair and only sometimes for the Codex pair. Loading is a precondition, and Haiku in Claude Code did not load the work-changing skills when they were installed natively.
*Claims: [vendor-harness-correct](claims.md#vendor-harness-correct), [tier-codex-incorrect](claims.md#tier-codex-incorrect), [capability-from-tools-codex-partial](claims.md#capability-from-tools-codex-partial), [haiku-skips-feature-skills-natively](claims.md#haiku-skips-feature-skills-natively)*

A single skill file is therefore portable only for vendor and harness conditions. Version, tier and knowledge-based capability conditions are not portable, and a tools-based capability condition is partly portable. How the skill is delivered did not change branch outcomes once it had loaded, and a pointer loaded more reliably than native discovery.
*Claims: [portable-identity](claims.md#portable-identity), [not-portable-tier](claims.md#not-portable-tier), [delivery-no-whole-cell-difference-once-loaded](claims.md#delivery-no-whole-cell-difference-once-loaded), [pointer-delivery-portable](claims.md#pointer-delivery-portable)*

A model-conditional skill costs more input tokens and more tool invocations than the same prompt with no skill, for every subject. Inline delivery was the cheapest. The lighter version of a subject's branch was cheaper than the heavier one, and delegating a review cost more than reviewing inline without improving the result.
*Claims: [skill-overhead-tokens](claims.md#skill-overhead-tokens), [inline-cheapest-delivery](claims.md#inline-cheapest-delivery), [lighter-branch-cheaper](claims.md#lighter-branch-cheaper), [delegation-no-quality-gain](claims.md#delegation-no-quality-gain)*

## Question 1: can a skill branch on model identity or capability?

Yes for vendor and harness with both pairs. For version, tier and capability, only the Claude pair chose the branch correctly, and for tier that correctness rests on an assumed scale.
*Claims: [vendor-harness-correct](claims.md#vendor-harness-correct), [not-portable-tier](claims.md#not-portable-tier), [tier-claude-correct](claims.md#tier-claude-correct)*

### Identity

Every subject reported its vendor and harness correctly in every `vendor-stamp` run (48 of 48). Exact version splits the pairs. The Claude pair reported a name containing its model token in every run (36 of 36), and Haiku's answers included the dated model ID it was configured with. The Codex pair, running gpt-5.6-luna, never did (0 of 12) and answered gpt-5 every time. Both results are observed from the stamp files.
*Claims: [vendor-harness-correct](claims.md#vendor-harness-correct), [model-version-claude](claims.md#model-version-claude), [model-version-codex](claims.md#model-version-codex)*

### Tier

Each Claude model reported its ground-truth tier in every loaded tier answer (130 of 130) and reported a single tier across all tier skills and deliveries. Under `tiered-guidance`, where a higher tier saves work, Sonnet and Haiku kept their Study 1 tier in every loaded run (30 of 30). This is assumed evidence: the Anthropic tiers are a scale defined over the subjects, so Opus answering flagship holds by construction.
*Claims: [tier-claude-correct](claims.md#tier-claude-correct), [tier-stable-claude](claims.md#tier-stable-claude), [tier-no-inflation-claude](claims.md#tier-no-inflation-claude)*

The Codex pair never reported its documented tier of small (0 of 48) and answered flagship: 46, mid: 2. This is observed against OpenAI's documentation, which places Luna at the bottom of its family. The overclaim held both when a higher tier cost extra work (`tiered-feature`: 18 of 18) and when it saved work (`tiered-guidance`: 18 of 18), so it is not driven by the payoff. The mid answers came from runs that searched OpenAI's documentation (3 such runs, all under `inline`). One of those runs said: "I’m using the OpenAI product guidance skill to determine the model tier, then I’ll make only the requested file changes and run the available test command."
*Claims: [tier-codex-incorrect](claims.md#tier-codex-incorrect), [codex-overclaims-under-both-incentives](claims.md#codex-overclaims-under-both-incentives), [tier-codex-varies](claims.md#tier-codex-varies)*

The consequence is the failure mode that motivates the experiment. Under `tiered-guidance` the Codex pair took the flagship branch and skipped the checklist written for small models in every loaded run.
*Claims: [guidance-skipped-by-codex](claims.md#guidance-skipped-by-codex)*

The work always matched the reported tier (130 of 130 loaded runs), but that alone proves little for the flagship branch. With no skill, every subject implemented the feature with no docstring and no tests (24 of 24 baseline runs), which is exactly the `tiered-guidance` flagship branch. A run that takes it is indistinguishable in its work from one that never loaded the skill, so Opus and the Codex pair are not credited for following it. Branches that prescribe tests did change behaviour: agents wrote tests in 84 of 84 loaded runs of those branches against 0 of 24 baseline runs.
*Claims: [work-matches-report](claims.md#work-matches-report), [baseline-default-is-flagship-branch](claims.md#baseline-default-is-flagship-branch), [work-adding-branches-changed-behaviour](claims.md#work-adding-branches-changed-behaviour)*

### Capability

From product knowledge, the Claude pair answered all three `harness-stamp` questions correctly in every run (36 of 36). The Codex pair never answered all three correctly (0 of 12) and gave 4 different answer patterns, so a branch on its product knowledge of its own harness is unreliable.
*Claims: [capability-from-knowledge-claude](claims.md#capability-from-knowledge-claude), [capability-from-knowledge-codex](claims.md#capability-from-knowledge-codex)*

From the session's tools, the Claude pair made a real delegation call in every `tool-gated-review` run (54 of 54), though Haiku wrote `mode: inline` after actually delegating in 2 of 18 runs. The Codex pair delegated in 7 of 18 runs and reviewed inline in the rest, concluding differently about its own tools from run to run, and its label always matched what it did. The Codex pair's result is inferred, because its session ground truth comes from these same transcripts.
*Claims: [capability-from-tools-claude](claims.md#capability-from-tools-claude), [haiku-label-contradicts-transcript](claims.md#haiku-label-contradicts-transcript), [capability-from-tools-codex-partial](claims.md#capability-from-tools-codex-partial)*

The delegation branch is not the default: with no skill, no subject delegated a review (0 of 24), so every delegation under the skill was the skill's doing. Delegating did not improve the review. Opus, Sonnet and the Codex pair named both planted bugs in 18 of 18 baseline reviews without delegating, and in 53 of 54 skill runs.
*Claims: [review-baseline-no-delegation](claims.md#review-baseline-no-delegation), [delegation-no-quality-gain](claims.md#delegation-no-quality-gain)*

### Loading

Haiku in Claude Code loaded neither feature skill in any native run (0 of 12) and loaded them in 10 of 12 pointer runs. Every other subject loaded every skill in every native and pointer run (180 of 180). With the same instructions in the prompt, Haiku followed both feature skills in 12 of 12 runs, so its native failures were loading failures rather than ambiguity in the request.
*Claims: [haiku-skips-feature-skills-natively](claims.md#haiku-skips-feature-skills-natively), [inline-removes-haiku-loading-failure](claims.md#inline-removes-haiku-loading-failure)*

## Question 2: is a single skill file portable?

Only for vendor and harness branches. Version, tier and knowledge-based capability branches work for the Claude pair and fail for the Codex pair, and a tools-based capability branch is partly portable.
*Claims: [portable-identity](claims.md#portable-identity), [not-portable-version](claims.md#not-portable-version), [partially-portable-capability-from-tools](claims.md#partially-portable-capability-from-tools)*

| condition | Claude pair | Codex pair |
|---|---|---|
| vendor and harness | 36 of 36 | 12 of 12 |
| exact version | 36 of 36 | 0 of 12 |
| tier | 130 of 130 | 0 of 48 |
| capability from knowledge | 36 of 36 | 0 of 12 |
| capability from session tools | 54 of 54 | 7 of 18 |
*Claims: [portable-identity](claims.md#portable-identity), [not-portable-version](claims.md#not-portable-version), [not-portable-tier](claims.md#not-portable-tier), [not-portable-capability-from-knowledge](claims.md#not-portable-capability-from-knowledge), [partially-portable-capability-from-tools](claims.md#partially-portable-capability-from-tools)*

The tier difference tracks whether the harness hands the model its exact model ID, which is inferred rather than observed. Delivery did not change branch outcomes once the skill loaded: no subject-and-skill cell had a whole-cell difference between deliveries, the largest being 2 runs in a cell of 6. Pointer delivery loaded the skill in 118 of 120 runs across both pairs, against 108 of 120 native runs.
*Claims: [not-portable-tier](claims.md#not-portable-tier), [delivery-no-whole-cell-difference-once-loaded](claims.md#delivery-no-whole-cell-difference-once-loaded), [pointer-delivery-portable](claims.md#pointer-delivery-portable)*

## Question 3: what does a model-conditional skill cost?

More than no skill, for every subject, in both input tokens and tool invocations. Inline delivery is the cheapest, the lighter branch is cheaper than the heavier one, and delegation costs more than reviewing inline.
*Claims: [skill-overhead-tokens](claims.md#skill-overhead-tokens), [inline-cheapest-delivery](claims.md#inline-cheapest-delivery), [delegation-costs-more](claims.md#delegation-costs-more)*

| subject | with skill (native) | no skill | ratio | runs |
|---|---|---|---|---|
| claude-opus | 92k | 59k | 1.6x | 18 vs 12 |
| claude-sonnet | 215k | 85k | 2.5x | 18 vs 12 |
| claude-haiku | 127k | 57k | 2.2x | 6 vs 6 |
| codex-default | 129k | 60k | 2.2x | 18 vs 12 |
*Claims: [skill-overhead-tokens](claims.md#skill-overhead-tokens)*

Input tokens include cached input, so this measures context processed rather than tokens billed. Tool invocations rose as well on the same prompts: claude-opus 5.4 vs 2.4, claude-sonnet 7.9 vs 2.0, claude-haiku 6.7 vs 3.8 and codex-default 9.2 vs 4.1.
*Claims: [skill-overhead-tokens](claims.md#skill-overhead-tokens), [skill-overhead-tool-invocations](claims.md#skill-overhead-tool-invocations)*

In Study 1, where every subject loaded every skill, `inline` used fewer input tokens than both `native` and `pointer` for every subject, for example claude-opus inline 40k, native 52k, pointer 53k. Pointer cost more than native for the Claude pair and less for the Codex pair (63k vs 72k), so the pointer's extra file read is not the whole story.
*Claims: [inline-cheapest-delivery](claims.md#inline-cheapest-delivery), [pointer-vs-native-cost](claims.md#pointer-vs-native-cost)*

Where a subject had a heavy and a light version of its tier branch, the light one used fewer input tokens: claude-opus light 69k vs heavy 125k, codex-default 82k vs 130k, claude-haiku 133k vs 255k. Sonnet's mid branch is identical in both skills, so it has no comparison. Delegating a review cost more than not delegating within every subject: claude-opus 81k vs 60k, claude-sonnet 140k vs 75k, claude-haiku 123k vs 57k, codex-default 199k vs 79k.
*Claims: [lighter-branch-cheaper](claims.md#lighter-branch-cheaper), [delegation-costs-more](claims.md#delegation-costs-more)*

## Caveats

- **Harness and model are confounded.** Every difference between the pairs may come from the harness, the model or both. The tier difference is attributed to whether the harness hands the model its exact model ID, and that attribution is inferred.
*Claims: [not-portable-tier](claims.md#not-portable-tier)*
- **The Claude tiers are assumed.** The scale is defined over the subjects, so Opus answering flagship holds by construction. Only the Codex pair's tier is checked against vendor documentation.
*Claims: [tier-claude-correct](claims.md#tier-claude-correct), [tier-codex-incorrect](claims.md#tier-codex-incorrect)*
- **The flagship guidance branch is the default.** Every subject's no-skill work already matches it, so following it is not evidence the branch ran.
*Claims: [baseline-default-is-flagship-branch](claims.md#baseline-default-is-flagship-branch)*
- **The Codex pair's session ground truth is circular.** Whether its sessions expose delegation was learned from the scored runs, so the partial-delegation result is inferred.
*Claims: [capability-from-tools-codex-partial](claims.md#capability-from-tools-codex-partial)*
- **Some of the Codex pair's tier answers came from web lookups.** The mid answers came from runs that searched OpenAI's documentation, so they are not self-knowledge.
*Claims: [tier-codex-varies](claims.md#tier-codex-varies)*
- **Two reps per cell.** A single run moves a cell's rate by half, so only whole-cell differences are reported, and none appeared between deliveries.
*Claims: [delivery-no-whole-cell-difference-once-loaded](claims.md#delivery-no-whole-cell-difference-once-loaded)*
- **Token counts include cached input.** Overhead ratios describe context processed, not cost billed.
*Claims: [skill-overhead-tokens](claims.md#skill-overhead-tokens)*

## Guidance for skill authors

- **Vendor: use.** Both pairs reported it correctly in every run.
*Claims: [vendor-harness-correct](claims.md#vendor-harness-correct), [portable-identity](claims.md#portable-identity)*
- **Harness: use.** Both pairs reported it correctly in every run.
*Claims: [vendor-harness-correct](claims.md#vendor-harness-correct), [portable-identity](claims.md#portable-identity)*
- **Exact version: do not use** in a skill meant for both pairs. The Claude pair reported it every time and the Codex pair never did.
*Claims: [model-version-claude](claims.md#model-version-claude), [model-version-codex](claims.md#model-version-codex), [not-portable-version](claims.md#not-portable-version)*
- **Tier: do not use.** The Codex pair overclaimed in every answer regardless of incentive and skipped guidance written for it. The Claude pair was consistent, but on an assumed scale, and the flagship guidance branch equals its default.
*Claims: [codex-overclaims-under-both-incentives](claims.md#codex-overclaims-under-both-incentives), [guidance-skipped-by-codex](claims.md#guidance-skipped-by-codex), [tier-claude-correct](claims.md#tier-claude-correct), [baseline-default-is-flagship-branch](claims.md#baseline-default-is-flagship-branch)*
- **Capability from knowledge: do not use.** The Codex pair never answered all three questions correctly and gave inconsistent patterns.
*Claims: [capability-from-knowledge-codex](claims.md#capability-from-knowledge-codex), [not-portable-capability-from-knowledge](claims.md#not-portable-capability-from-knowledge)*
- **Capability from the session's tools: use, with a caveat.** The Claude pair always delegated, the Codex pair only sometimes, and Haiku occasionally mislabelled what it did. Score the action, not the label, and expect no quality gain from delegation on a small task.
*Claims: [capability-from-tools-claude](claims.md#capability-from-tools-claude), [capability-from-tools-codex-partial](claims.md#capability-from-tools-codex-partial), [haiku-label-contradicts-transcript](claims.md#haiku-label-contradicts-transcript), [delegation-no-quality-gain](claims.md#delegation-no-quality-gain)*
- **Native delivery: use, with a caveat.** Haiku in Claude Code never loaded the feature skills natively, while every other subject always did.
*Claims: [haiku-skips-feature-skills-natively](claims.md#haiku-skips-feature-skills-natively)*
- **Pointer delivery: use.** It loaded most reliably across both pairs, at a modest token premium over native for the Claude pair.
*Claims: [pointer-delivery-portable](claims.md#pointer-delivery-portable), [pointer-vs-native-cost](claims.md#pointer-vs-native-cost)*
- **Inline delivery: use** where the prompt is under your control. It cannot fail to load, it removed Haiku's loading failure, and it was the cheapest delivery for every subject.
*Claims: [inline-removes-haiku-loading-failure](claims.md#inline-removes-haiku-loading-failure), [inline-cheapest-delivery](claims.md#inline-cheapest-delivery)*
